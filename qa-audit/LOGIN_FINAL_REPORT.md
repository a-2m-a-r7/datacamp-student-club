## ما اختُبر

| المسار | التحقق |
|---|---|
| دخول البريد | الحقول المطلوبة، رفض البيانات الخاطئة، إعادة المحاولة، تطبيع البريد، العودة للتاب المطلوب |
| العضو والأدمن | دخول الإدارة بهوية أدمن؛ منع بحث العضو؛ البريد غير المؤكد لا يُقبل اعتمادًا على علامة البروفايل |
| الجلسة | إعادة التحميل، الخروج وإعادة التحميل، انتهاء refresh token، عدم فقد الإدخال عند سباق التهيئة |
| التسجيل | حساب يحتاج تأكيدًا دون session؛ الاحتفاظ بالبريد وعرضه عربيًا وإنجليزيًا بعد إعادة التحميل |
| تأكيد البريد | إعادة الإرسال، الدخول بعد التأكيد، تحديث الجلسة من الهوية التي أكدها الخادم |
| الاستعادة | فشل المزود و429، إعادة المحاولة، redirect الصحيح، كلمة ضعيفة وغير متطابقة، حفظ جديد وخروج فعلي |
| الروابط المنتهية | رسالة واضحة وزر طلب رابط/دخول جديد؛ لا تحويل ناجح وهمي |
| Google | طلب اختيار الحساب والـ callback الصحيح، إلغاء المستخدم، وجهة داخلية آمنة |
| Callback | انتظار SDK؛ استبدال PKCE مرة واحدة فقط عند عدم وجود session؛ عدم استبدال الكود ثانية عند وجود session |
| لوحة المفاتيح | إظهار وإخفاء كلمة المرور بزر قابل للتركيز والتشغيل |

## الإصلاحات

- صفحة التحقق كانت تعيد صاحب التسجيل الجديد إلى Login لأنه لا يمتلك session بعد. البريد المنتظر محفوظ مؤقتًا في sessionStorage، وإعادة الإرسال تعمل دون جلسة. كلمة المرور لا تُحفظ هناك.
- واجهة التحقق الإنجليزية كانت تقرأ user.email رغم غياب user؛ أصبحت تستخدم البريد المنتظر أيضًا.
- callback ينتظر تهيئة SDK ويشارك عملية حل الجلسة بين إعادة تشغيل effect؛ يدعم كود PKCE المتبقي بتبادل واحد أو الجلسة التي جهزها SDK، ويمنع الاستبدال المكرر.
- غياب session والرابط المنتهي والإلغاء لا يوجّه إلى Dashboard باعتباره نجاحًا. توجد إجراءات واضحة للعودة.
- تحديث كلمة المرور ينهي جلسة الاستعادة قبل عرض العودة إلى Login؛ إعادة تحميل Login لا تعيد المستخدم تلقائيًا للحساب القديم.
- تحقق البريد يعتمد على email_confirmed_at من Auth، ثم refreshSession عند تغير الحالة؛ علامة is_verified في البروفايل لا تتجاوز التحقق.
- تبديل الهوية يمحو بيانات وصلاحيات الحساب السابق أثناء تحميل البروفايل الجديد. استجابة الجلسة القديمة بعد unmount لا تُعتمد.
- وجهات العودة تقبل مسارات الموقع الداخلية وتستبعد الوجهات الخارجية وصفحات الدخول التي تسبب حلقات.
- Forgot Password لا يدعي الإرسال عند غياب إعداد الخدمة. روابط التسجيل وإعادة التأكيد تستخدم /auth/callback.
- أُزيل مصدر التسجيل المكرر لحدث login، وادعاء +10 XP في التسجيل الذي لا يثبت حفظ مكافأة؛ تحسنت صيغة البريد وإتاحة زر كلمة المرور.

## فحوص Supabase الحقيقية

يسجل [login-live-results.json](login-live-results.json) إعداد Auth واستجابة رفض حقيقية لبيانات حساب غير موجود: البريد وGoogle مفعّلان، تأكيد البريد مطلوب، الدخول غير الصحيح يرجع 400/invalid_credentials، وبدء Google يرجع 302 إلى accounts.google.com مع select_account. لم يُنشأ حساب، ولم تُرسل رسائل استعادة، ولم تتغير كلمات مرور المستخدمين.

هذه الفحوص لا تثبت إكمال موافقة Google أو وصول رسالة إلى صندوق البريد. المالك قال إنه سيجرب حسابه بنفسه؛ نتيجة هذه التجربة لم تصل عند إعداد التقرير. يحتاج تسليم البريد الحقيقي مزود بريد وحدود إرسال مناسبة؛ تفعيل email provider وحده ليس إثبات تسليم الرسائل.

## العزل وإعادة التشغيل

اختبارات الدخول تشغل Supabase JS الحقيقي مع استبدال نقل Auth/REST ببيانات QA؛ تؤكد عقد التطبيق والجلسة والـ callbacks، ولا تدعي إنشاء مستخدمي Supabase حقيقيين. الاختبارات المنشورة تستخدم نفس العزل وتمنع كل طلب كتابة غير معالج ببدائل QA.

```powershell
npm run lint
npm run build
$env:QA_RESULTS_FILE='qa-audit/login-final-results.json'
npx playwright test --config=qa-audit/fixes.config.ts login-final
```

لإعادة اختبار الواجهة المنشورة: عيّن QA_SUPABASE_URL إلى أصل Supabase المرتبط بالنسخة حتى تعترض البدائل طلباته، ثم شغّل login-deployed.config.ts. يتوقف الإعداد دون هذا الأصل. لا تستخدم حسابًا حقيقيًا أو كلمات مرور حقيقية في الاختبارات.
