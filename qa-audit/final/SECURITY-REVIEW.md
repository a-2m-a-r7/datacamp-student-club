# Security review notes - 17 October 2026

Production was excluded from tests and mutations. The isolated QA schema has 34 RLS tables and explicit client/server grants. BUG-024's coordination table and its two SECURITY INVOKER functions deny anon/authenticated use and are excluded from Realtime. Local all-table source-grant CRUD probes pass 816/816; the hosted ACL check independently verifies the new table/RPC grants.

The exact-value scan found no occurrences of the approved QA secrets in delivery candidates, client builds or reachable Git blobs in its recorded run. Its later extension also checks JSON-escaped private-key strings. Generic scanning remains complementary and cannot prove every possible secret is absent.

The broader generic history scan found one API-key-shaped value in the historical Firebase web-client configuration, at fingerprint `c89367de5229e32d`, Git object `b9a929f5f8ca`. Offline inspection shows only Firebase client fields (apiKey/authDomain/projectId/storageBucket/messagingSenderId/appId/firestoreDatabaseId), with no private key. It is not the newly created QA Gemini key or a Supabase server key. No request was made using that historical value, and history was not rewritten.

[Firebase's official guidance](https://firebase.google.com/docs/projects/api-keys) distinguishes public client identifiers from authorization credentials and requires appropriate API restrictions, especially exclusion of Gemini for publicly accessible keys. The historical project's restrictions were not verified because production/account settings were outside this audit's scope. Treat that restriction check as an owner review item; do not claim a confirmed credential breach or silently report a zero-finding pattern scan.

Supabase security advisors also report intentional RLS tables without client policies, a public_events SECURITY DEFINER projection containing published event fields only, publicly callable guarded RPCs/trigger functions, and leaked-password protection disabled. These notices require contextual review; they are not all privilege-escalation findings. Public projection privacy, untrusted promotion denial and guarded RPC access were tested separately. The public_events projection omits registrations/attendance data; trigger functions cannot be used as ordinary RPCs. Do not grant client policies to server-only tables to silence an informational notice.
